# Results: Lambda Web Functions in front of Aurora — do you still need RDS Proxy?

All numbers below come from the runs in `results/raw/` (one directory per run). The tables are generated by
`python scripts/summarize.py results/raw`. Nothing is typed by hand.

## Setup

- Region eu-west-1. Aurora PostgreSQL 17.11, one writer `db.t4g.medium` (2 vCPU, `max_connections` = 401). Seed: 1,000,000 customers and 5,000,000 orders, 717 MB.
- The request is `GET /customer/:id?delay_ms=N`: one lateral-join query (last 20 orders of the past 90 days), then `pg_sleep(N ms)` on the same connection. `delay_ms` 0 is scenario A (pure DB work). `delay_ms` 100 is scenario B (the connection is held while the handler "waits", as with a slow downstream call).
- Variants, same query code (`app/shared/customer.mjs`):
  - `event-direct`: Event Function (Node 24, arm64, 1024 MB) behind a Function URL, one `pg.Client` per execution environment, direct to the writer.
  - `event-proxy`: same code, connecting through RDS Proxy (`require_tls`).
  - `web-pool`: Web Function (Node 24, arm64, fixed 2 vCPU / 2 GB per environment) running Express with a `pg.Pool` (`POOL_MAX` 10, endpoint `maxEnvironments` 20).
- Load: k6 2.3.0 on one `c7g.large` in the same VPC. Constant VUs, no think time, 3 minutes per run, 60 s pause between runs. Every variant gets a 2-minute warm-up (200 VUs, `delay_ms` 100) that is not counted.
- Between variants the Event Function environments are recycled (an environment variable change) and leftover connections of the app user are terminated. Each variant starts with an empty database.
- No reserved concurrency on the Event Functions.

## How to read the columns

- **req/s**: all responses (any status) divided by the run duration.
- **200**: share of responses with HTTP 200.
- **p50 / p95 / p99**: k6 `http_req_duration` over all responses, including errors. Where a run has many 429s the percentiles mostly describe the 429s.
- **envIds**: distinct execution environments seen in successful responses (each environment generates a UUID at start).
- **DB conns (app)**: peak of connections the database sees with this variant's `application_name`, sampled from `pg_stat_activity` every 5 s. RDS Proxy passes the client's `application_name` through, so for `event-proxy` this is the proxy's connections to the database for the app.
- **Aurora conns max** / **Aurora CPU max**: CloudWatch, 1-minute maximum, limited to the minutes of the run. CloudWatch is coarser than the sampler and can miss short peaks.
- **cold starts**: Event Functions: `REPORT` lines with `@initDuration`. Web Function: `platform.initReport` events. Both from CloudWatch Logs Insights over the exact run window.

## What the numbers show

1. **Event Functions open one database connection per environment; the Web Function opens environments × `POOL_MAX`.**
   In scenario B at 500 VUs, `event-direct` reached 283 environments and 284 app connections. It returned 7,853 HTTP 500s (97.1% 200) with p99 5,016 ms.
   `event-proxy` reached 563 environments. RDS Proxy held up to 390 database connections (`max_connections` is 401) and the run kept 99.9% 200 with p99 1,298 ms.
   `web-pool` used 12 environments and 120 connections (12 × 10), with 100% 200.
2. **Idle Event environments keep their connection.** `event-direct` at 10 VUs (scenario A) shows 201 app connections, left open by the environments of the 200-VU warm-up.
   `event-proxy` at 10 VUs (scenario B) shows 391, left by the previous 500-VU run. `pg.Pool` in `web-pool` closes idle connections after 10 s.
3. **In scenario B, `web-pool` is bound by the pool, not by compute.** At 200 VUs it ran on 5 environments (about 40 concurrent requests each) and 50 connections. Its p50 was 465 ms, against 134 ms for `event-direct` and 126 ms for `event-proxy`.
   The pool test confirms it. With `POOL_MAX` 5 / 10 / 20 the environments stayed at 5, and throughput went 238 / 476 / 893 req/s with p50 749 / 343 / 202 ms.
   The Web Function scales on concurrency per environment. Requests waiting for a free pool connection inside an environment do not make it add environments. With a pool, `POOL_MAX` per environment is the setting that matters.
4. **Scenario A saturates the database CPU.** From 50 VUs the 1-minute maximum of Aurora CPU is 93–98% for every variant.
   At 500 VUs it stays at 96–98% for at least two consecutive minutes in all three variants, so the plan's stop criterion (CPU > 95% for 2 minutes) was met. The runs were not stopped and are reported as they are.
   The p99 of about 5 s at 500 VUs for `event-direct` and `web-pool` matches the client's `connectionTimeoutMillis` of 5,000 ms. Scenario A mostly measures the database, not the connection model.
   At 200 VUs `web-pool` hit `maxEnvironments` 20: 5,319 × 429 `Platform.EndpointMaxEnvThrottle`.
5. **Cold spike (0 → 500 VUs in 30 s).**
   - `web-pool`: 12 cold starts (average init 400 ms), 120 DB connections, 100% 200.
   - `event-direct`: 501 cold starts, peak of 253 app connections, CloudWatch 500 Aurora connections, 6,365 × 500 (96.6% 200).
   - `event-proxy`: 501 cold starts, 387 DB connections, 2 × 500, p99 1,152 ms.
6. **`maxEnvironments` protects the database by rejecting the excess.** With the cap at 2 and 500 VUs, only 3.1% of responses were 200. The rest were:
   - 1,288,601 × 429 `Platform.EndpointMaxEnvThrottle`
   - 478,501 × 429 `Platform.EndpointRequestThrottle`
   - 128,429 × 503

   k6 retries immediately, so it pushed 10,750 req/s. On the database side, the 12 environments of the previous run kept serving for about 40 s (120 connections). After that the app held 20 connections (2 × `POOL_MAX`) for the rest of the run. Lowering the cap is not instant.
7. **Lambda cost per million requests (computed, not billed).**
   - `web-pool`: 0.35–0.46 USD from 50 VUs up.
   - `event-direct`: 0.25–2.26 USD in scenario A and 1.62–4.54 USD in scenario B.
   - `event-proxy`: similar to `event-direct`, plus the fixed RDS Proxy charge (2 vCPU × 0.016 USD = 0.032 USD per hour for this instance).

   Event Functions are billed for the 100 ms wait, and their duration grows when the database is saturated. The Web Function is billed for active CPU and memory.
   For `web-pool` the memory part is approximated as maximum memory × `EnvironmentActiveTime`, because the billing model for memory is not fully documented (`lab.md`, section 10). Billed costs from Cost Explorer are added separately.

## Limits and what was not run

- One run per cell. No repetitions, so no variance.
- Only the third attempt is reported. The first was discarded because the database was full of leftover connections from idle Event environments and RDS Proxy. The second was lost when the load generator terminated itself before its results were copied (see `lab.md`).
- Some pauses between blocks were longer than 60 s because the orchestrating laptop went to sleep (about 57 minutes before `event-proxy`, about 105 minutes before the cold spike). Every block still started with the same reset, terminate and warm-up.
- The cold spike ran without a fresh environment recycle right before each variant. Environments were recycled at 12:21 UTC, there was no traffic from about 11:10 UTC, and the spikes ran from 12:56 to 13:06 UTC. Leftover app connections were terminated before each variant (200 before `web-pool`, 0 before `event-direct`, 253 before `event-proxy`).
- `event-proxy` at 10 VUs, scenario B: 30 requests hit k6's 60 s timeout in the same second. The cause was not investigated. These timeouts explain its 27 req/s and its cost per million.
- CloudWatch reports 504 Aurora connections in `event-direct` at 500 VUs (scenario B) and 500 in its cold spike, above `max_connections` 401. Not investigated.
- Latency percentiles include error responses.
- `throttleConfig.rateLimit`, reserved concurrency on the Event Functions and Aurora Serverless were not tested.

## Docs vs reality

1. Concurrency per Web Function environment starts low and is learned: 2 → 8 → 20 in about 15 s of traffic in the CLI spike. A new function behind a tight `maxEnvironments` rejects most requests until it ramps. This is why every variant gets a warm-up.
2. This account's Web Functions quotas were 200 vCPU and 10,000 RPS, against documented defaults of 2,000 vCPU and 100,000 RPS. `Platform.AccountRequestThrottle` appeared at about 12,900 req/s.
3. CloudFormation creates the Web Function with `FunctionName` only. The API requires a revision and an endpoint configuration at creation.
4. `AutoDeploymentMode` exists in the API but not in the CloudFormation schema of `WebFunctionEndpoint`. `RevisionWeights` with the revision at 100 is needed.
5. Lambda does not check that the server is listening: a revision and an endpoint can be `Active` with a broken app. Send a test request after each deploy.
6. The RDS Proxy certificate is signed by Amazon Root CA (ACM), not the RDS CA. A `pg` client given only the RDS bundle fails with `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`. Use `[...tls.rootCertificates, rds-global-bundle]`.
7. In a discarded attempt, RDS Proxy kept about 100 database connections for over 30 minutes with zero clients.
